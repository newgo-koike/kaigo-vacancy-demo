プロジェクト概要
介護施設の空き状況をリアルタイムで可視化し、病院・ケアマネが施設に直接問い合わせできるプラットフォームの開発プロジェクト。
役割分担
YUMEMATCH（製作） システム設計・開発・デプロイ・技術的な維持管理
兵頭さん（依頼） 施設・病院・ケアマネへの営業・交渉・関係構築。要件・方針の最終決定

サービス概要
検索側（病院・ケアマネ）：退院調整・入居先探しの電話確認が不要になる。空室をリアルタイムで把握し直接問い合わせ。
掲載側（介護施設）：高額な紹介会社への手数料（20〜30万円/件）から解放。低コストで入居者を直接獲得。
競合（紹介会社）：「空室確認ツール」として位置付け、複雑なケースでは共存できる可能性もある。

Phase 2：施設が自分で空室を更新する仕組み — 実装案
以下3案のうち1つを採用する。YUMEMATCHが実装を担当。選択はコスト・施設側の操作ハードルを考慮して兵頭さんと合意の上決定する。
案A
Googleフォーム ＋ スプレッドシート ＋ GAS
★☆☆ 最も簡単
▌ データフロー
施設担当者がGoogleフォームを送信 → スプレッドシートに自動記録 → GASがJSONに変換してGitHubにpush → サイトがJSONを読み込んで即時反映
▌ 実装内容（YUMEMATCH作業）
① Googleフォームを作成（施設名・個室空き数・多床室空き数・更新者名の4項目）
② スプレッドシートとフォームを連携（送信で自動行追加）
③ GASスクリプトを作成：スプレッドシートを読んでJSONを生成 → GitHub APIでpush
④ サイトのHTMLをJSONを参照する構造に書き換え（fetch + 動的レンダリング）
⑤ GitHub Pagesにデプロイ先を移行（JSONと同リポジトリ）
※GASのトリガーを「フォーム送信時」に設定すると送信後1〜2分以内に反映
月額コスト
¥0
全部Google無料枠
実装工数
3〜5日
設計〜テストまで
反映速度
1〜2分
GAS実行ラグあり
▌ 懸念点
⚠ GASの無料枠（1日6分実行）を超えると動かなくなる。施設数が増えたら要注意
⚠ フォームURLを知っていれば誰でも送信できる（施設の認証なし）
⚠ GitHubへのpushにGitHub Personal Access Token（PAT）の管理が必要
△ 施設ごとに専用フォームを用意するか、施設名をプルダウンで選ばせるか設計が必要
✏️ 案Aへのコメント・判断
案B
施設専用の更新URL（メールOTP ＋ Supabase）
★★☆ 本格的
▌ データフロー
週1でメールを自動送信「空室状況を更新してください」 → メール内リンクをクリック → 施設専用フォームが開く → Supabase DBに書き込み → サイトがSupabaseを参照して即時反映
▌ 実装内容（YUMEMATCH作業）
① Supabaseでテーブル設計：facilities（施設マスタ）, vacancies（空室履歴）
② 施設ごとにランダムなURLトークンを発行・DB保存（アカウント不要でURL認証）
③ 更新フォームページを作成（URLトークンで施設を特定→送信→Supabase更新）
④ Resend または SendGrid でリマインダーメールを定期自動送信（週1回）
⑤ サイトのフロントエンドをSupabase参照に書き換え（fetch Supabase REST API）
⑥ RLSポリシー設定（施設は自施設データのみ更新可能）
月額コスト
¥0〜500
Supabase無料枠で当面OK
実装工数
2〜3週間
DB設計〜メール送信まで
反映速度
即時
送信と同時に反映
▌ 懸念点
⚠ URLトークンは推測困難だが、メールを転送されると第三者が更新できてしまう
⚠ Supabase無料枠は月50万行・帯域5GB。施設数が増えたら有料プランへ（月$25〜）
△ メール送信サービス（Resend等）の初期設定が別途必要
△ 施設担当者がメールを見ない場合、更新されない（リマインダー設計が重要）
✏️ 案Bへのコメント・判断
案C
LINE Messaging API（LINEで送るだけ）
★★★ 施設ハードル最低
▌ データフロー
施設担当者がLINEに「個室2 多床室0」と送信 → Webhook → Cloudflare Worker がテキストをパース → SupabaseまたはKV Storeに書き込み → サイトが即時反映
▌ 実装内容（YUMEMATCH作業）
① LINE公式アカウント（Messaging API）を開設
② 施設ごとにLINE友だちとして登録（または施設をグループに招待）
③ Cloudflare WorkerでWebhookを受信：LINEユーザーID → 施設を特定
④ メッセージをパース：「個室:数字 多床室:数字」の書式を認識
⑤ SupabaseまたはCloudflare KV（このプロジェクトでは既存Worker活用）にupsert
⑥ パース失敗時はLINEでエラー返信「送信形式: 個室2 多床室1」
⑦ サイトのフロントエンドをDB参照に書き換え
月額コスト

実装工数
3〜4週間
Webhook〜パーサー開発

▌ 懸念点
⚠ LINE公式アカウントの月額固定費が発生（無料プランはメッセージ数制限あり）
⚠ テキストのパース精度：「個室が2つ空きました」等の自然文には対応できない
⚠ 施設ごとにLINE友だち追加・初期設定のオンボーディングコストが高い
△ 誤送信時の取り消し・修正フローを別途設計する必要がある
△ 将来的にClaude APIと組み合わせれば自然文パースも可能（AIコスト追加）

✏️ 採用案の決定・理由
懸念点と対策
開発・運用上のリスク。兵頭さんの判断が必要な点は✏️欄に記入してください。
🔄 データの鮮度
施設が空室情報を更新し続けてくれるかがサービス価値の核心。更新が止まると「古い情報しかない」と離脱される。
✏️ 対策・判断 兵頭さん
🏢 施設の登録促進
掲載施設が少ないと病院・ケアマネが使わない（鶏と卵問題）。初期は無料掲載で施設数を増やす必要がある。
✏️ 対策・判断 兵頭さん
⚖️ 紹介会社との競合
既存の紹介会社が施設・病院との関係を持っている。「空室確認ツール」として位置付けて棲み分けるか検討が必要。
✏️ 対策・判断 兵頭さん
🔒 個人情報・コンプライアンス
施設の担当者名・電話番号の掲載には施設側の同意が必要。利用規約・プライバシーポリシーの整備も必要。
✏️ 対策・判断 兵頭さん
👥 運用継続性
YUMEMATCH（製作者）・兵頭さん（依頼者）どちらがどこを担うかを明確にしないと止まる。属人化リスクもある。
